SKILL: jira-change-to-pr  (implement a Jira change, compile, test, verify and raise a pull request)

WHEN TO USE
The user asks to make / implement / fix a change for a Jira ticket and raise (create/open) a pull request, e.g.
"make the change for CMDM-8449 and raise a PR", "implement this Jira and create a pull request in mdm-integration".

BASE BRANCH RULE - ALWAYS develop, NEVER master
- Default base branch across all repositories is develop.
- NEVER refer to or use master as a base branch for code analysis or changes. Master branch is not in sync with develop.
- All code analysis must happen ONLY on the feature branch created from develop.

TOOLS (local workspace + git)
workspace_cloneRepo, workspace_createBranch, workspace_listFiles, workspace_readFile, workspace_searchText,
workspace_replaceInFile, workspace_writeFile, workspace_runMaven, workspace_gitStatus, workspace_gitDiff,
workspace_commitAndPush, workspace_createPullRequest.
(Git MCP tools spring_ai_mcp_client_git_mcp_server_* are also available).

WORKFLOW - execute the steps in order:

1. UNDERSTAND THE JIRA
   - Use the pre-fetched issue from the prompt (or jira_getIssue). Also jira_getIssueComments if the description is thin.
   - Note what must change, acceptance criteria, affected module/connector/field/API, constraints.
   - If the requirement is unclear: STOP and ask the user specific questions. Do not invent requirements.

2. GATHER KNOWLEDGE (skill confluence-research)
   - confluence_searchContent with Jira key, system/connector name, key terms when documentation is needed.
   - Extract design rules, field mappings, naming and test conventions. Cite pages (title + link).

3. IDENTIFY THE REPOSITORY (skill jira-repo-context)
   - Resolve repository (e.g. ifw-microservices/<repo>).
   - Check for existing work: search_pull_requests(query: "<KEY> repo:ifw-microservices/<repo>").
     If an open PR already exists for this key, inform user and ask whether to add to it; do not open a duplicate PR.

4. FIRST CREATE FEATURE BRANCH FROM develop (MANDATORY BEFORE ANY CODE ANALYSIS)
   - The feature branch MUST be created from develop BEFORE analyzing or reading code!
   - Clone / checkout the repository on develop into the workspace:
     workspace_cloneRepo(repo: "<repo>", branch: "develop")
   - Create and check out the feature branch from develop:
     workspace_createBranch(repo: "<repo>", branch: "feature/<JIRA-KEY>", fromBranch: "develop")
     (If using Git MCP: create_branch(owner: "ifw-microservices", repo: "<repo>", branch: "feature/<JIRA-KEY>", from_branch: "develop"))
   - If develop branch is NOT present in the repository, STOP and ASK the user which branch should be used to create the feature branch.
   - If feature/<JIRA-KEY> already exists and is not yours to reuse, use feature/<JIRA-KEY>-<2-3 word slug>.
   - NEVER commit to develop, master, main, release/* or any protected branch.

5. DO CODE ANALYSIS IN FEATURE BRANCH ONLY
   - Code analysis MUST be done ONLY in the feature branch created from develop.
   - NEVER refer to master as a base branch to analyze what code change is required (master is not in sync with develop).
   - Read and inspect files using workspace tools (the workspace is checked out on the feature branch):
     workspace_listFiles(repo: "<repo>", path: "<module>/")
     workspace_searchText(repo: "<repo>", query: "<symbol|field|topic>")
     workspace_readFile(repo: "<repo>", path: "<path>")
     (If reading via Git MCP tools, always specify ref: "refs/heads/feature/<JIRA-KEY>").
   - Design the smallest correct change adhering to existing style, logging, and test patterns.

6. SHOW CODE DIFFERENCE & TAKE CONSENT (MANDATORY - HUMAN-IN-THE-LOOP)
   - NEVER modify files, commit, push, or open a pull request without presenting the changes and getting user consent first.
   - Present the proposal clearly to the user:
     a) Target repository (`ifw-microservices/<repo>`), target feature branch (`feature/<JIRA-KEY>`), and base branch (`develop`).
     b) Summary of changes and rationale based on Jira acceptance criteria and Confluence guidelines.
     c) File-by-file unified diff in standard ```diff ``` code blocks showing additions (+) and deletions (-).
     d) Ask for confirmation with a clear call to action:
        "Please review the proposed file changes above. Reply with 'Accept' / 'Proceed' (or click Accept in the UI) to make the code changes, compile, test, verify with spring-boot:run, and raise the pull request, or tell me what to modify."
   - STOP HERE. Output NO tool calls for editing files, committing, or raising PRs in this turn. Wait for user consent.

7. ON USER CONSENT: MAKE CODE CHANGE (DO NOT REWORK STEPS 1-6)
   - Only when user responds with acceptance ("Accept", "Proceed", "Yes", "Create PR", "Confirm", "Looks good"):
   - DO NOT re-read Jira, DO NOT search Confluence, DO NOT re-clone repository, DO NOT re-create branch, and DO NOT re-analyze code.
   - The feature branch is ALREADY created from develop and the code changes and test cases are ALREADY finalized in Step 6.
   - Proceed DIRECTLY to apply the approved changes to the files in the feature branch:
     workspace_replaceInFile(repo: "<repo>", path: "<path>", oldText: "...", newText: "...")
     or workspace_writeFile(repo: "<repo>", path: "<path>", content: "...")
     (or push_files if using Git MCP).

8. COMPILE AND TEST
   - Compile and run tests in the local workspace:
     workspace_runMaven(repo: "<repo>", goals: "clean test", args: "-pl <module> -am")
     (or without -pl if repository root / multi-module changes).
   - If compilation or tests fail, see Step 11.

9. RUN LIKE mvn spring-boot:run AND VERIFY LOG
   - Run the Spring Boot application in the workspace:
     workspace_runMaven(repo: "<repo>", goals: "spring-boot:run", args: "-pl <module>")
   - Inspect the logs to verify the application starts up cleanly without errors, port conflicts, or failed bean creation.
   - If startup or runtime issue occurs, see Step 11.

10. RAISE PULL REQUEST IF SUCCESSFUL
    - Verify git status and diff:
      workspace_gitStatus(repo: "<repo>") and workspace_gitDiff(repo: "<repo>")
    - Commit and push all changes to origin on the feature branch:
      workspace_commitAndPush(repo: "<repo>", message: "<JIRA-KEY>: <short summary>")
    - Open the pull request targeting develop as base branch:
      workspace_createPullRequest(repo: "<repo>", title: "<JIRA-KEY>: <Jira summary>", head: "feature/<JIRA-KEY>", baseBranch: "develop", body: "<Markdown body with Jira link, what changed, how tested, and runtime log verification>")
    - Report to user: PR link, branch, base branch (develop), changed files, test results, and runtime log verification.

11. HANDLE TEST FAILURE, COMPILATION FAILURE, OR RUNTIME ISSUE
    - If compilation fails, tests fail, or runtime issue occurs during spring-boot:run:
      * Analyze the error logs and stack traces.
      * Fix the issue in the code or tests on the feature branch.
      * MANDATORY: If additional code changes are required beyond what the user previously approved, STOP and TAKE CONSENT AGAIN from the user before proceeding!
      * Once user consents to additional changes, re-run compile, test, and spring-boot:run verification.
      * Only raise the pull request when compile, test, and runtime log verification are ALL successful.
