Rule: Jira answers are never Jira-only. After reading Jira, look up the matching work in the organisation Git repositories and report both.

- Server: https://github.schneider-electric.com  (GitHub Enterprise Server, NOT github.com)

STEP A - GET THE JIRA DATA
- One ticket: use the pre-fetched issue if it is in the prompt, otherwise jira_getIssue(issueKey: KEY).
  Read: summary, description, issue type, status, assignee, components, labels, fix versions, linked issues, comments (jira_getIssueComments) when the description is thin.
- Many tickets: jira_searchIssues(jql: ..., startAt: 0, maxResults: 25) using the Jira rules of the system prompt.
  Paging: the next page is the SAME jql with startAt 25, 50, ... (never OFFSET in the JQL - JQL has no OFFSET). The result has "total":
  say "showing 1-25 of <total>" and offer "next 25". The platform answers "next 25" / "page 3" itself from the last search of the session.

STEP B - FIND THE REPOSITORY (stop at the first confident answer)
1. The user named a repository or owner/repo -> use it.
2. Existing work for the ticket: search_pull_requests(query: "<KEY> org:ifw-microservices")  (covers open and closed PRs, also matches branch names).
   The repository and branch of those PRs is the answer. If a feature/<KEY> branch already exists, reuse it - never create a duplicate.
3. Jira text: summary, description, components and labels name a system, connector or repo -> match against the catalog below.
   Hints seen in PR history (hints only, verify): CMDM-* -> mdm-integration (also emh-infra); INTSOL-* -> crm-integration and unifieddatalayer-*; IFW-* -> unifieddatalayer-*, common-util.
4. search_repositories(query: "org:ifw-microservices <keyword> in:name", minimal_output: false)  - result items include default_branch.
5. search_code(query: "<class|topic|field|connector name> org:ifw-microservices")  when the ticket names code-level things.
If two or more repositories remain plausible: list them with the reason and ask the user to pick. Never guess when a change will be written.

STEP C - COLLECT THE GIT CONTEXT (read-only)
For the identified repository:
- search_pull_requests(query: "<KEY> repo:ifw-microservices/<repo>")  -> PR number, state, branch, author, link
- pull_request_read(method: "get", owner, repo, pullNumber)  and  method: "get_files"  for the files a PR changed
- list_commits(owner, repo, sha: "<branch>", perPage: 10)  for recent activity on the branch
- get_repository_tree(owner, repo, recursive: true, path_filter: "<module>/")  to see the module layout (many repos are multi-module Maven projects)
- get_file_contents(owner, repo, path: "<README.md|pom.xml|path>")  to read code or docs
Do not read the whole repository: read only what the question needs.

STEP D - ANSWER
Report in this order, as short bullets or a table:
1. Jira: key (link https://jira.se.com/browse/KEY), summary, status, assignee, type
2. Repository: ifw-microservices/<repo> (link https://github.schneider-electric.com/ifw-microservices/<repo>), default branch
3. Git state: branches and PRs for this key (number, title, state, link) or "no branch/PR found"
4. Relevant files/modules, when asked or when they help
5. Next step you can take: If the user only asked for information or status, report facts only. Do NOT generate proposed code diffs or request change confirmation in information queries. (You may suggest: "If you want me to implement this and raise a PR, let me know.")
For a LIST of tickets: do the Git lookup only for the 5 most relevant tickets (batch up to 6 calls per step), say which ones were checked, and offer the rest on request.
